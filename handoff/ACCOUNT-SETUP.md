# Account setup

What has to exist in the Dengage panel before this build stores a row, and how the SDK is called on
each surface. Every name here is exact: a table, a column or a call spelled differently is accepted
and stored nowhere.

`tools/check-contract.mjs` reads the column tables below and fails when the code writes a column
this document does not ask for.

## How the SDK is called

| Call | Shape |
|---|---|
| `initialize` | Takes an object: `{ contactKey }` or `{ deviceId }` or both, plus `pageView`, `cartItems`, `language`, `currency` and `location`. A bare string is not the contract |
| Inbox provider | Constructed with `new dengage('InboxMessageProvider')`, and needs Web SDK 2.4.0 or later |
| Inbox scope | Serves anonymous visitors as well as identified ones. `ckey` is attached once identified |
| `getMessages` | Serves a 30 second cache, so two reads in the same moment return the same list |
| Inbox expiry | 7 days, default and maximum |
| Wishlist | `ec:addToWishlist` and `ec:removeFromWishlist`, which let the SDK fill the identifiers. Reaching `wishlist_events` through `sendDeviceEvent` also works but makes `event_id`, `event_type` and `is_used` the caller's problem, and a missing `event_id` means the row is accepted and never stored |
| `getNotificationPermission` | Four values, not three |
| Injection script | Generated by the panel and pasted whole |

## The Custom Inbox, server to server

`reference/inbox-rest-api` has two endpoints and neither creates a message. `GET /api/inbox/getMessages`
reads a contact's mailbox. `POST /api/inbox/events` reports what happened to a message already
there: an impression, an open, a click, a delete. Messages arrive from a campaign or a journey.

What it adds is a surface without an SDK, which is a telecom touchpoint rather than a technicality:
the contact centre and the retail counter read a customer's mailbox by contact key from a backend
and show an agent what was sent. `dtelco-inbox` serves that panel and refuses `POST`, because an
agent glancing at a customer's messages has not read them on the customer's behalf.

`reference/inbox-rest-api` gives every path relative and names no host. Measured 4 September 2026
against the documented `400` error shape with no account data: `tr-push.dengage.com` and
`tr-event.dengage.com` answer, `tr-api.dengage.com` answers 404, and `tr-inapp.lib.dengage.com`
answers a missing bucket key. The push host serves it, which is the host in `js/config.js` under
`datacenters.tr.push`.

## `sendInstant` and transactional push are different capabilities

`reference/sendtransactionalpush` addresses one person and takes a saved content id: every word
comes from a content prepared beforehand. `reference/sendinstantpush` takes `applicationIds` and an
inline `content` of `title`, `message` and `targetUrl`, and goes to an application's tokens, or to a
`segmentId` or `tableId` if one is named.

That difference is why a network operations centre can use the second one: nobody writes the
wording of an outage in advance. `dtelco-broadcast` serves it, refuses without `confirm: true`, and
reports who it will reach before it reaches them.

## What the documentation confirmed unchanged

The core of the integration: `pageView` with its nine page types and the same
columns; `ec:addToCart`, `ec:removeFromCart`, `ec:deleteCart`, `ec:beginCheckout` with
`cartItems` as the whole cart every time; `ec:order` and `ec:cancelOrder` with the same
`payment_method` vocabulary; `ec:search`; `sendDeviceEvent(table, data)` into a Big Data table
that must relate to `master_device`, with `key` and `event_date` filled by the SDK and never
sent; `setContactKey`; `getToken` returning null until permission is granted; 30 requests per
second per IP on the REST API; and the instruction to cache the login token rather than log in
before every call.

## Panel setup this build needs

Each line is what the documentation requires.

1. **Settings > Applications > New > Website.** Needs an application name, the **website domain
   URL**, and an **icon or badge URL**.
2. **Enable Push Notifications**, then choose the **Custom Permission Prompt type**.
3. **Leave "Show Permission Prompt on page load" OFF.** With it on, the prompt fires
   unprompted on load, and Chrome counts a dismissed unprompted dialog against the origin, which
   can poison push for every later attempt from that machine. The storefront asks from a button
   instead.
4. **Download the service worker file** and place it at the **origin root**. Only one service
   worker may generate a web push token: any other must be removed first, and its prompts
   disabled, or two providers fight over the subscription.
5. **Copy the injection script** from More > Setup Guide and send it to me. It replaces one file.
6. **Add every domain** the SDK runs on with **+ Add Domain**.
7. **Safari on macOS needs a certificate**: an Apple Developer account, a Website Push ID, a CSR,
   a `.cer` exported as `.p12` with a password, uploaded under Push Notification > Safari.
   Without it there is no macOS Safari push at all. Android Chrome and Windows Chrome need none
   of this.
8. **The custom event table `dtelco_events` must be a Big Data table** related to
   `master_device`, created before any page sends to it. Until it exists every row is accepted
   and stored nowhere, with no error.

   **Twelve columns, and every one of them is written by the site.** Three are required on every
   `sendDeviceEvent` row and nine are the payload. A column missing here is a value the page
   sends and the table drops, silently, which is the failure mode this table has:

   | Column | Type | What it carries |
   |---|---|---|
   | `event_id` | text | Required. A UUID per row |
   | `event_type` | text | Required. One of the closed vocabulary in `js/dengageEvents.js` |
   | `is_used` | boolean | Required. Always false on write |
   | `product_id` | text | The product the row is about, or a comma joined list on a comparison |
   | `product_type` | text | plan, device, accessory, roaming, fixed and the rest |
   | `rule` | text | Which recommendation or creative rule produced the row |
   | `source` | text | web, newsletter, launcher, bss, care, store |
   | `placement` | text | popup, bar, inline, for a creative row |
   | `amount` | text | A number as text. Decision 62 records that both text and numeric work |
   | `note` | text | The one free field, and the only one a person reads |
   | `destination` | text | The roaming zone a travel date was given for |
   | `horizon` | text | The travel date itself, which is what journey 13 times off |

   `tools/check-contract.mjs` reads the columns the site actually writes and fails if this table
   does not name every one of them, so a new field cannot be added to a payload without being
   added here first.

## The custom columns on `master_contact`

Twenty seven, created in the panel before anything writes to them. A column that does not exist is
a value accepted and stored nowhere, exactly as with the custom event table, and with no error at
either end. `tools/check-contract.mjs` reads the columns the two writers actually send and fails if
this list does not carry every one of them.

**Written by `dtelco-persona-seed`**, from the operator's own record, and refreshed by running it
again after the simulator changes a plan or a lifecycle:

`msisdn`, `plan_id`, `plan_name`, `plan_type`, `lifecycle`, `arpu_band`, `esim`, `device_model`,
`contract_end`, `family_lines`, `preferred_store`, `preferred_channel`

The relay writes web form values and the operator function reports `tells_dengage: false`,
because a simulator writing contact fields would be pretending a page can do what a page cannot.
So without this writer a segment on `plan_name`, or a message printing `$Contact.lifecycle`, finds
them empty and nothing says so.

**Written by `dtelco-lead-relay`**, from what a visitor typed or did:

`whatsapp_consent`, `last_nps`, `focus_product_id`, `focus_product_title`, `focus_product_brand`,
`focus_product_category`, `focus_product_price`, `focus_views`, `last_watch_product_id`,
`last_watch_list`, `reco_product_id_1`, `reco_product_id_2`, `reco_product_id_3`, `reco_rule`,
`reco_at`

`whatsapp_consent` is a custom column rather than a permission, and the difference is worth saying
out loud in the room. `reference/updatecontactsbulk` documents exactly two permission columns,
`email_permission` and `gsm_permission`. There is no WhatsApp permission on `master_contact`, so a
WhatsApp consent is a value the operator's own compliance holds and a journey or a segment reads as
a condition. It is not a suppression the platform enforces.

The standard columns beside them, `contact_key`, `name`, `surname`, `email`, `gsm`,
`email_permission` and `gsm_permission`, exist already and need creating nowhere.

**`city` is not one of them.** Measured 4 September 2026 against this account: a `/bulk/contacts`
call carrying it was refused with

    code 1, Column does not exist: city, msisdn, plan_id, plan_name, plan_type, lifecycle,
    arpu_band, esim, device_model, contract_end, family_lines, preferred_store, preferred_channel

so `city` is created with the other twelve. That refusal is also the shape to expect while any
column is missing: HTTP 400, a readable message naming every one, and nothing written. It is the
one place in this integration where a missing column says so out loud rather than accepting the
value and dropping it, and it is worth showing a room for exactly that reason.

## The egress address, and when a proxy is needed

An account that allowlists a single address needs every REST call to arrive from that address.
Serverless backends do not have one: Supabase Edge Functions were measured leaving from five
different addresses on five consecutive calls, so an allowlist refuses calls that carry correct
credentials. The refusal is `403` with an empty body, which is indistinguishable from a missing
permission, and that is the trap worth naming.

`GET dtelco-preflight` tells the two apart. It reports which credential name it resolved, the
address the call left from, and what `/login` answered, and it sends nothing and writes nothing.

Where an allowlist is in force, set `DTELCO_API_PROXY` to a host that holds the allowlisted
address and forwards to the account. Every function honours it. The proxy holds no credentials of
its own: each call carries its own login body or bearer token and the proxy forwards them, so the
proxy is a network path rather than a second place a credential lives.

Credential names are resolved in order: `DENGAGE_USERKEY` and `DENGAGE_PASSWORD` first, then the
account's own naming. A credential present under a different name reads as configured rather than
as missing.

## Values supplied at setup

| Input | What it enables |
|---|---|
| `accountId` and `appGuid` | The SDK loader URL, and the site leaves dry mode. Set in `js/config.js` |
| The panel's injection script | Replaces `tools/partials/dengage-snippet.html` |
| Confirmation the service worker is at the origin root | No service worker, no web push at all |
| Web SDK version 2.4.0 or later | Below that there is no `InboxMessageProvider` |
| API user key and password, with transactional permission | Every REST call |
| The egress address allowlisted | REST calls are refused before credentials are read |
| `DTELCO_API_PROXY` | Optional. The base URL of a host that holds the allowlisted address, no trailing slash. Set it and every REST call leaves from there; unset, calls go direct. See below |
| Firebase integration key, from the Android application in the panel | `Dengage.init` will not subscribe the device without it |
| `google-services.json` | The Android build fails without it |
| The **Custom Inbox** application guid | Its own application type, created separately from web push. Without it the counter panel reports a misconfiguration rather than reading a mailbox, which is deliberate: `dtelco-inbox` will not substitute the push guid |
| `inbox_enabled` on the account | "On a disabled account every request is rejected with `400`", and a 400 cannot be told apart from a wrong account id from outside the panel |
| The push permission on the API user | `sendInstant` answers 403 with an empty body to an API user without it |
